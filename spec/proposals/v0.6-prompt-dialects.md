# Proposal — Codec prompt dialects (v0.5 / v0.6 candidate)

**Status:** design — not yet in any version of the spec. Candidate for
v0.5 or v0.6. Sister proposal to v0.5's wire-overhead reductions
(`docs/WIRE_OVERHEAD_PROPOSAL.md`) and the static-string bit-mapping work
already tracked in `/home/willi/.claude/plans/ok-lets-start-a-valiant-bachman.md`.

**Companion reference:** `packages/bench/docs/COMPRESSIBLE_PROMPTS.md`
(prompt-engineering patterns for naturally compressible model OUTPUT).
This proposal addresses the orthogonal axis: **per-concept substitution
dictionaries for compressible INPUT and OUTPUT at the language layer**.

---

## TL;DR

Codec already crushes wire bytes at two layers:

1. **Token-native framing** (msgpack/protobuf instead of JSON-SSE) —
   ~10× over JSON-SSE at default identity encoding.
2. **HTTP Content-Encoding with dict-zstd** — ~1700× over JSON-SSE on the
   v0.4.1 cross-stack matrix when content cooperates.

This proposal adds a **third orthogonal layer at the language tier**:
opportunistic per-concept substitution against a model-and-corpus-specific
dictionary. Same information density, fewer tokens, no quality loss
because every substitution is individually measured to be model-understood.

Stacked savings from a 7-token English snippet:

| Layer                                | Result                  |
|--------------------------------------|-------------------------|
| English JSON-SSE                     | ~7 tokens × 14 B = 100 B|
| + Codec msgpack identity             | ~7 tokens × 2 B  =  14 B|
| + dialect substitution (this proposal)| ~3 tokens × 2 B =   6 B|
| + dict-zstd                          | ~3 tokens × 0.5 B =  2 B|

Each layer multiplies. The v0.4.1 bench measures only layers 1-2. This
proposal adds layer 3.

---

## The mechanism

A **prompt dialect** is a content-addressed dictionary
`{english_phrase → compressed_form}` where each entry has been individually
measured against a target tokenizer + model. Construction process:

1. Sample a representative corpus of typical prompts + responses for the
   workload (medical, legal, code, customer support, …).
2. For each frequent concept, enumerate candidate compressed forms:
   emoji, CJK character, math symbol, abbreviation, country code,
   programming-style notation, single-letter shorthand.
3. For each candidate, measure two things:
   - **Token cost** against the target tokenizer (deterministic, cheap).
   - **Comprehension quality** against the target model (a test prompt
     compares model output for English vs compressed input; score with
     embedding similarity + task-specific eval).
4. Keep candidates where `token_cost(compressed) < token_cost(original)`
   AND `quality_score(compressed) ≈ quality_score(original)` within
   tolerance.
5. Output: a substitution dictionary, per (tokenizer, model) pair.
6. Runtime preprocessor applies the dict to outgoing prompts; postprocessor
   inverts incoming responses.

The dictionary is **per-model derivative** — Claude's dict is different
from GPT-4's, which is different from Llama's. Each gets its own optimum.

Hybrid prose is fine: any phrase without a measured substitution stays as
English. The dialect is opportunistic, not total.

## Potential dictionary — quality-test required per model

These are more aggressive substitutions whose comprehension varies by
model. Include only after measuring against your target model.

### CJK character substitutions

For models with strong Chinese training (Qwen, DeepSeek, GPT-4o,
Claude 3.5+):

| English   | Substitution | Notes                                  |
|-----------|--------------|----------------------------------------|
| `dragon`  | `龍`         | Often 1 token in CJK-aware tokenizers |
| `fire`    | `火`         | Universally recognized                 |
| `water`   | `水`         | Universally recognized                 |
| `mountain`| `山`         | Universally recognized                 |
| `human`   | `人`         | Single-token, semantically rich        |
| `time`    | `時`         | Often 1 token, formal                  |
| `large`   | `大`         | Single-token quantifier                |
| `small`   | `小`         | Single-token quantifier                |
| `new`     | `新`         | Single-token modifier                  |
| `old`     | `古`         | Classical Chinese, semantically rich   |

Quality test: prompt the model with both English and CJK versions of the
same query; embedding similarity of responses should exceed 0.95.

### Aggressive abbreviations

These need per-model testing because the model may misinterpret without
context:

| English        | Substitution | Risk           |
|----------------|--------------|----------------|
| `request`      | `req`        | Generally safe |
| `response`     | `resp`       | Generally safe |
| `function`     | `fn`         | Code contexts only |
| `variable`     | `var`        | Code contexts only |
| `argument`     | `arg`        | Code contexts only |
| `position`     | `pos`        | Stable         |
| `temperature`  | `T`          | Risk: collides with "T" as time |
| `pressure`     | `P`          | Risk: collides with "P" as power |
| `value`        | `v`          | Too short, semantic collisions |

### Set/logic operators

For models with strong math training:

| English        | Substitution | Notes                             |
|----------------|--------------|-----------------------------------|
| `union`        | `∪`          | Set context                       |
| `intersection` | `∩`          | Set context                       |
| `complement`   | `¬`          | Logic context                     |
| `and`          | `∧`          | Logic context (risk in prose)     |
| `or`           | `∨`          | Logic context (risk in prose)     |
| `xor`          | `⊕`          | Logic / circuit context           |

These work great in math/logic prompts, may confuse the model in prose.

### Domain-specific (medical, legal, finance)

Each domain has its own short-form vocabulary. ICD-10 codes for medical
diagnoses, ISO country codes for finance, Bluebook citations for legal.
Per-domain dictionaries layer on top of the base dialect. Building these
is a corpus-collection exercise for each target community.

## Wire integration — Codec protocol extension

Tokenizer maps grow a new optional field:

```json
{
  "id": "qwen/qwen2",
  "vocab": {...},
  "merges": [...],
  "zstd_dictionaries": [...],
  "prompt_dialects": [
    {
      "name": "codec-shorthand-v1",
      "url": "https://raw.githubusercontent.com/wdunn001/Codec/main/dialects/codec-shorthand-v1.json",
      "hash": "sha256:...",
      "scope": "agent-to-agent",
      "target_tokenizer": "qwen/qwen2",
      "target_model_family": ["qwen2.5", "qwen2"],
      "measured_token_reduction": 0.34,
      "quality_eval_corpus_sha256": "sha256:...",
      "min_quality_score": 0.95
    }
  ]
}
```

Each dialect entry includes:
- **`name` / `hash`** — content-addressed identifier
- **`url`** — fetch location for the dictionary JSON
- **`scope`** — `agent-to-agent` | `human-readable` | `domain-medical` | …
- **`target_tokenizer` / `target_model_family`** — what the dict was built for
- **`measured_token_reduction`** — average % token savings across the eval corpus
- **`quality_eval_corpus_sha256`** — pin to the corpus the quality was measured on
- **`min_quality_score`** — measured embedding-similarity floor

Client that understands a dialect:
1. On startup, fetch dict from `url`, verify hash, cache locally
2. Before sending each prompt, run substitutions in dictionary order
3. After receiving each response, apply inverse substitutions back to English
4. Surface `Codec-Prompt-Dialect: codec-shorthand-v1 sha256:<hex>` response
   header so observability tools can see which dialect was active

Server-side:
- The server doesn't need to know about the dialect — it just sees tokens.
- Optional `Accept-Prompt-Dialect` request header lets server-side
  middleware confirm what dialect the client is using (for logging /
  policy enforcement).

### Quality fallback

If runtime quality drops (e.g., model returns garbled responses to
compressed input), client falls back to native English. Detection:
similarity check on a few canary substitutions per N requests; if
quality_score < min_quality_score for K consecutive requests, drop the
dialect and log a warning.

## Why this stacks with Codec's existing layers

| Layer | Dictionary | Wire effect          | Mechanism                        |
|-------|------------|----------------------|----------------------------------|
| Wire (Codec dict-zstd) | sha256-keyed bytes pre-trained on token streams | bytes/token ↓ | LZ77 + Huffman with dict prefix |
| Language (this proposal) | concept→short-token pre-measured per (model, corpus) | tokens/request ↓ | Opportunistic substitution |

The wire dict crushes byte-level redundancy in stream framing. The
language dict crushes token-level redundancy in semantic encoding. They
are **orthogonal**: applying both gives the product of their independent
savings.

A worked example with the v0.4.1 numbers, hypothetical 30% token-reduction
dialect:

| Configuration | tokens | bytes/token (Codec msgpack + dict-zstd) | wire bytes |
|---------------|-------:|----------------------------------------:|-----------:|
| English baseline | 2048 | 0.14 (sglang's measured rate) | 291        |
| + dialect (30% reduction) | 1434 | 0.14 | 200 (≈) |
| Effective ratio vs JSON-SSE identity | — | — | ≈ 2,400× |

The current sglang 1,707× becomes ~2,400× with a modest 30% language-layer
reduction. A more aggressive 50% reduction takes it past 3,000×.

## Risks + open questions

1. **Per-model dictionary drift.** When the target model retrains, the
   dictionary may need rebuilding. → Mitigation: version dicts by content
   hash, run quality CI on each new model release.

2. **Roundtripping degrades semantics.** Each translation hop can lose
   nuance. → Mitigation: only substitute concepts that round-trip
   identically; measure with embedding similarity, not surface-form match.

3. **Mixed-dialect prompts.** A complex prompt may benefit from medical
   shorthand in one part and code shorthand in another. → Solution:
   support stacked dialects with `scope` axes; client applies each
   independently.

4. **The dialect itself is data the client must fetch.** First-request
   cost is the dict download (probably tens of KB). → Mitigation: same
   as zstd dicts — content-addressed, cached by hash indefinitely.

5. **Cryptographic / privacy posture.** Substitutions are deterministic,
   so an observer can infer the original by reversing the dictionary.
   This is fine for typical agent traffic; not a security feature.

6. **Quality eval cost.** Building a dialect requires running the eval
   corpus through the model many times. This is the construction-time
   cost; runtime is just dict lookup. → Acceptable for offline build
   pipelines.

## Initial build pipeline

`packages/bench/scripts/build-prompt-dialect.py` (NEW for v0.5):

```python
# 1. Load reference corpus (e.g., packages/bench/methodology/prompts.json)
# 2. For each candidate substitution in the initial dict (this file):
#    - Tokenize original prompt with target tokenizer
#    - Tokenize substituted prompt
#    - Verify token_cost(substituted) < token_cost(original)
#    - Submit both to the target model
#    - Score responses with embedding similarity
#    - If quality ≥ min_quality_score: keep the substitution
# 3. Emit JSON: {entries: [{english, compressed, savings, quality_score}, ...]}
# 4. Hash the JSON → sha256 identifier
# 5. Commit to dialects/codec-shorthand-v1-${tokenizer}-${model}.json
```

The same pipeline can drive domain-specific dialect construction by
swapping the eval corpus.
