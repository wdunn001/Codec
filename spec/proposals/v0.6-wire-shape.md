# v0.6 proposal: frame shape, header conformance, and the consensus minimum

**Status:** proposal. Not executed.
**Measured with:** `packages/bench/scripts/frame_shape_bench.py`, run against
`packages/bench/golden/qwen2.json` (287 real Qwen2.5-7B-Instruct token ids).

Codec's argument is that text is the wrong wire format. The msgpack frame
undercuts that argument. It spends most of a small frame on the ASCII strings
`ids`, `done`, and `finish_reason`. This proposal closes that gap. It also
brings the `Codec-*` header set onto the HTTP field standards. It then cuts the
negotiation surface down to what a server needs before it can emit a first
frame.

---

## 1. Frame shape

### 1.1 What a frame costs today

A single non-final one-token msgpack frame:

```
0x82                    fixmap, 2 entries            1 byte
0xa3 'i' 'd' 's'        key "ids"                    4 bytes
0x91 0xcd 0x25 0xeb     [9707] as uint16             4 bytes
0xa4 'd' 'o' 'n' 'e'    key "done"                   5 bytes
0xc2                    false                        1 byte
                                                    15 bytes
```

Ten of those fifteen bytes are key names and map scaffolding. The token is four.

### 1.2 Measured alternatives

Bytes per token, streaming the golden corpus at the given tokens per frame:

| Shape | 1 | 4 | 8 | 16 | saving at 1 |
|---|---:|---:|---:|---:|---:|
| `{"ids": [...], "done": false}` (today) | 14.77 | 5.78 | 4.27 | 3.64 | 0.0% |
| `{"i": [...], "d": false}` | 9.72 | 4.48 | 3.60 | 3.28 | 34.1% |
| `{0: [...], 1: false}` | 7.72 | 3.98 | 3.35 | 3.15 | 47.7% |
| `{0: [...]}`, `done` present only when true | 5.73 | 3.48 | 3.10 | 3.03 | 61.2% |
| `[[...], false]` positional | 5.72 | 3.47 | 3.09 | 3.02 | 61.3% |
| `{0: bin(LEB128 ids)}` | 6.03 | 3.03 | 2.53 | 2.28 | 59.2% |
| `{0: base, 1: bin(zigzag deltas)}` | 4.73 | 3.68 | 2.99 | 2.64 | 68.0% |
| protobuf, canonical proto3 | 8.03 | 3.53 | 2.78 | 2.40 | 45.6% |
| protobuf, as the engine forks emit it | 10.02 | 4.03 | 3.02 | 2.52 | 32.1% |

Three results here change what the spec should say.

**Integer keys plus a sparse `done` beat canonical protobuf at every chunk size
up to 8.** The spec presents protobuf as the more efficient wire mode. That ranking is an
artifact of msgpack carrying string keys. Neither format is inherently ahead.

**The engine forks pay 2.0 bytes per token for nothing.** Their protobuf encoder
appends `b"\x10\x00"` on every frame. proto3 omits an implicit-presence scalar
at its default value. A canonical encoder therefore writes no `done` field on a
non-final frame. The forks' output runs 25% larger than canonical protobuf at
one token per frame. It is also not what a generated proto3 encoder produces for
the same message. Fixing it takes one conditional in three files.

**Delta-varint wins only at one token per frame.** At 4 tokens and above, plain
LEB128 ids in a `bin` blob beat it (2.28 against 2.64 at 16). Deltas between
adjacent ids in real text are large and near-random. Zigzag encoding therefore
buys little, while the base-id field costs a byte. The v0.5 headline feature is
being sold on a number measured at its single best chunk size.

### 1.3 Recommendation

Add `stream_format: "msgpack-compact"`, defined as:

```
{ 0: [ids...], 1: done?, 2: finish_reason?, 3: tool_calls? }
```

Integer keys. `done` omitted when false. A decoder defaults every absent key.
The change is therefore wire-additive under the existing versioning policy. A
v0.5 client that negotiates `"msgpack"` keeps byte-identical output.

Positional arrays measure a hair better at 5.72 against 5.73. Reject them. They
leave nowhere to add a field. `msgpack-delta` already needs `base_id`.

Take `{0: bin(LEB128 ids)}` as `"msgpack-packed"` for batched streams. It is the
strongest option measured there. Keep both. The picker already chooses per
stack. It can choose per chunk-size profile too.

Correct the "theoretical floor: raw uint32, 4.0 bytes/token" line in
`spec/versions/v0.5.md`. It is not a floor. Three shapes here already beat it.
One of those three is `msgpack-delta`. v0.5 specifies that one itself.

## 2. Header conformance

### 2.1 Findings

`X-Codec-Map` appears 18 times on the request side. RFC 6648 deprecated the
`X-` prefix in 2012. Three names now exist for one concept: `X-Codec-Map`,
`Codec-Map`, `Codec-Tokenizer-Map`.

No field uses [RFC 9651](https://www.rfc-editor.org/rfc/rfc9651) structured
field syntax. Every `Codec-*` value is an ad-hoc string parsed by hand in six
languages. That gives six places for a parse divergence to become an interop
bug.

`Codec-Tokenizer-Map-Hash: sha256:<64 hex>` reinvents
[RFC 9530](https://www.rfc-editor.org/info/rfc9530/). That RFC defines digests
as a structured-field dictionary pairing an algorithm with a base64 value. Base64 of
a sha-256 is 44 characters against 64 for hex. The standard form is therefore
shorter. It also keeps all 256 bits. `docs/WIRE_OVERHEAD_PROPOSAL.md` §2
proposes truncating to 16 hex to save bytes. Base64 saves more. It discards
nothing.

The map URL should be an [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288)
`Link` relation. That form composes with a Subresource-Integrity style
`integrity` attribute.

None of the fifteen `Codec-*` names is registered with IANA. RFC 9110 §18.4
requires registration. `docs/submissions/draft-dunn-codec-00.md` states an intent
to submit.

### 2.2 `Vary` is incomplete. This is a live cache-poisoning bug

Every spec version emits `Vary: Accept-Encoding` and nothing else. The v0.4
graceful-downgrade rule makes the response depend on `Codec-Client-Version`.

This is not theoretical. In `codec_compression.py` the same function sets both:

```python
headers: dict = {"Vary": "Accept-Encoding"}
...
if client_version is not None:
    headers = filter_codec_headers(headers, client_version)
```

The identical pairing is in sglang (both branches), vllm (both branches), and
llama.cpp (`server-context.cpp` sets `res->headers["Vary"] = "Accept-Encoding"`).
A shared cache in front of any of them will serve a v0.3 client the response
shaped for a v0.5 client. `codec-supervisor` runs behind nginx-proxy today. The
path is reachable in the current deployment.

Fix: `Vary: Accept-Encoding, Codec-Client-Version`. Two lines per engine.

### 2.3 `Vary: stream_format` is inert

`spec/versions/v0.5.md` instructs servers to vary on `stream_format`. That is a
request **body** field. RFC 9110 §12.5.5 restricts `Vary` to header field names.
The directive therefore does nothing. A body-driven negotiation on POST is not
cacheable through `Vary` at all. Moving `stream_format` to a request header is
the only way to make the sentence true.

### 2.4 Recommendation

Collapse the set into one registered RFC 9651 dictionary field:

```
Codec: v=0.5, map="qwen/qwen2", map-int=:YsL5T8vbm0nVFjIxTmSqZYlElrw5dRy5CGYElleiYq0=:,
       dict=:7MlBCgmx0+XHqB...:, pol="acme/strict-v3", sess=:o/jAFA==:
```

One name for HPACK and QPACK to index once. One parser per language, backed by
existing structured-field libraries. Digests in the RFC 9530 form. A natural
home for the `Codec-Session` idea already proposed. Keep `Link:` for the
discoverable map URL. Retain the legacy names as a deprecated alias set gated on
`Codec-Client-Version < 0.6`. The existing downgrade table already specifies
that gating.

## 3. The consensus minimum

Two negotiation mechanisms exist for one decision set. The shipping path is
stateless HTTP, re-answered on every response. The specified path is the
HELLO/READY exchange, carried across four spec versions, implemented by no
engine, and encoded in JSON inside a binary protocol.

Walking the eight HELLO axes against what a server must know before frame one:

| Axis | Needed before frame 1 | Notes |
|---|---|---|
| `accept_encoding` | yes | standard `Accept-Encoding` already carries it |
| `stream_format` | yes | msgpack, protobuf, or a variant |
| `Codec-Client-Version` | yes | drives graceful downgrade |
| `accept_safety_policies` | conditional | only when policy negotiation is on |
| `accept_decoders` | latents only | irrelevant to text |
| `accept_pipelines` | latents only | irrelevant to text |
| `accept_tokenizers` | **no** | see below |
| `modalities` | **no** | fixed by the endpoint that was called |
| `accept_transports` | **no** | the client chose one by connecting |

`accept_tokenizers` reads as a negotiation and is not one. A server serving
Qwen2.5 emits Qwen2 ids. A client that cannot decode them fetches the map or
fails. The server has no alternative to offer. The axis is therefore a client
assertion the server can only reject. It belongs in a pre-flight check or an
error path. The natural answer is a `409` carrying the map reference.

That leaves wire format, compression, and version. Compression is standard HTTP.
The other two fit in the `Codec:` field from §2.4. The whole negotiation then
becomes one request header and one response header.

**HELLO/READY needs a decision.** Implement it in at least one engine during
v0.6, or move it to `spec/proposals/`. Four versions of unimplemented normative
text is a cost the IETF draft will pay for. If it stays, re-encode it. A msgpack
or CBOR handshake belongs in a binary protocol.

## 4. Protobuf field 4 is claimed twice

`spec/versions/v0.5.md` line 65 says v0.5 adds "a new optional `int32 base_id =
4` in the protobuf message". The normative `message CodecFrame` block at line
291 of the same file still carries only fields 1, 2, and 3. The spec therefore
contradicts itself. The field was never actually written down.

Meanwhile all three engines ship `repeated ToolCall tool_calls = 4` and serve it
to clients from `GET /codec/schema` for code generation:

- `sglang/srt/entrypoints/codec_frame.py` (both branches)
- `vllm/entrypoints/codec_frame.py` (both branches)
- `llama.cpp/tools/server/server.cpp`

`tool_calls` appears nowhere in any spec version. A client generating a decoder
from the spec and a client generating one from `/codec/schema` disagree about
what field 4 is. They disagree across wire types too: varint against
length-delimited.

Resolution: `tool_calls` ships in three engines while `base_id` ships nowhere.
`tool_calls` therefore keeps 4. Write it into the normative block. Give
`base_id` field 5. Correct line 65.

```proto
message CodecFrame {
  repeated uint32   ids           = 1 [packed = true];
  bool              done          = 2;
  optional string   finish_reason = 3;
  repeated ToolCall tool_calls    = 4;   // shipped since v0.4.1
  optional int32    base_id       = 5;   // msgpack-delta / protobuf-delta
}
```

## 5. Sequencing

The frame work is worthless until the engines are current. Every Codec branch
was last touched in May 2026. sglang sits 4,688 commits behind upstream. The two
sglang branches have diverged far enough that neither is a superset of the
other. Consolidate and rebase first.

1. Consolidate to one Codec branch per fork. Rebase onto upstream.
2. Land the two-byte protobuf `done` fix and the `Vary` fix. Both are small.
   Both are pure wins. Neither needs a spec change.
3. Write field 4 and field 5 into the normative proto block.
4. Add `msgpack-compact` and `msgpack-packed` to the spec, then to the six
   client packages and three engines in one batch. The key strings appear in
   nine places. A partial rollout produces silent decode failures.
5. Register `Codec:` with IANA and ship the structured-field form behind
   `Codec-Client-Version >= 0.6`.
6. Decide HELLO/READY.
